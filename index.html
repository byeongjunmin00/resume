공동구매 도메인 설계 및 구현

  • 참여 인원 구간별로 단가가 내려가는 규칙을 별도 엔티티로 분리해, 상품마다 다른 할인 구간을 데이터로 정의하고 코드 변경 없이 바꿀 수 있도록 설계.
  • 여러 명이 동시에 참여할 때 정원을 넘기는 문제를 비관적 락과 원자적 UPDATE 두 방식으로 각각 구현하고, 부하테스트로 두 전략을 비교해 선택 근거를 남김.
  • 원자적 UPDATE 경로에서 참여 INSERT 를 먼저 실행하면 FK 검사가 잡은 공유 락 위에서 정원 증가가 배타 락 승급을 기다리다 데드락이 나는 것을 재현. 정원 증가를 먼저 실행하도록 순서를 바꿔 해소.
  • 미결제 참여를 정리하는 만료 처리가 확정 결제만 보고 판정해 결제 진행 중인 참여자의 자리까지 회수하던 문제를 발견해 수정. 돈은 빠져나갔는데 팀에는 없는 상태가 될 수 있었음. 진행 중인 결제는 유예하되, 방치된 결제 시도가 자리를 영구 점유하지 않도록 유예에 상한을 둠.
  • 정원 변동을 커밋 이후에만 브로드캐스트해 롤백된 참여가 화면에 반영되지 않도록 이벤트 발행 시점을 고정.
결과
동시 참여가 몰려도 정원과 확정 단가가 어긋나지 않습니다.

결제 처리와 환불 구현

  • 결제 생성·조회와 환불 요청 처리를 구현. 같은 환불 요청에 승인이 동시에 여러 번 들어오면 전부 성공하던 경합을 발견. 잠금을 걸어도 그대로 재현되어, 소유권 확인과 상태 검사를 나눠 하던 흐름을 첫 조회부터 잠금 조회로 통일해 해결. 동시 승인 8회 중 8회 성공하던 것이 1회만 성공하도록 바뀐 것을 검증.

실시간 1:1 상담 구현

  • WebSocket·STOMP 로 1:1 상담을 구현하면서, 한 지점만 막아서는 경계가 서지 않아 연결·구독·발행 세 지점 모두에서 참여자 여부를 검사. 인증된 사용자가 자신이 참여한 상담방에만 접근하도록 경계를 고정.
  • 메시지는 저장에 성공한 경우에만 발행되도록 순서를 고정해, 화면에는 보이는데 기록에 없는 메시지가 생기지 않도록 처리.

Redis 캐시 SPOF 제거

  • 테스트 중 인기 검색어 응답이 캐시를 타지 않는 것을 확인하고 원인을 추적해, Rate Limit·인기 검색어는 Redis 장애 시 통과하는데 캐시 계층만 예외인 것을 발견. 조회 성능을 위해 붙인 캐시가 서비스 필수 의존이 되어 있던 상태.
  • Redis 를 실제로 중단시켜 상품 목록·상세가 500 을 반환하는 것을 재현.
  • 캐시 계층을 fail-open 으로 전환해 캐시 오류 시 DB 직접 조회로 넘어가도록 변경, 장애 중에도 200 응답 유지.
결과
구매자가 캐시 장애 중에도 상품 조회와 구매를 중단 없이 이어갈 수 있습니다.

프로덕션 OOM 근본 원인 규명

  • 메모리 상한을 두 차례 조정했는데도 재시작이 반복되자 설정값이 아닌 다른 원인을 의심하고, 운영 컨테이너에 직접 접속해 JVM 이 인식한 자원 값과 실제 할당량의 차이를 확인.
  • 진단 도구가 없는 런타임 이미지였던 탓에 이미지를 임시로 교체해 스레드 덤프를 확보하고, 메모리를 잠식하던 스레드가 컨테이너 자원 오인식에서 비롯된 것임을 규명.
  • JVM 이 참조하는 코어 수를 실제 할당량으로 고정. 해당 스레드가 48개 → 2개로 줄어든 것을 운영 환경에서 재측정해 확인.

예측 불가능한 서버 재시작이 사라졌고, 현재 RSS 610MB / 컨테이너 한도 954MB 로 안정 가동 중입니다.

  • 실패율이 뛰는 지점에서 p95 가 오히려 낮아진 것을 근거로, 병목이 DB 커넥션 풀이 아니라 Tomcat 의 연결 수용 한계임을 판단.
  • 락 방식을 바꾸면 개선될 것이라는 가설은 측정값에 차이가 없어 기각하고, DB 커넥션 풀 기본값(10) 과 로그인 해싱 비용을 다음 후보로 지목. 두 요인을 분리하는 재측정은 하지 못함.

AI 상담 오류 처리와 운영 지표

  • 외부 API 에 기대는 기능이 주문·결제 같은 핵심 흐름을 흔들지 않아야 한다고 보고 실패를 전제로 설계. LLM 호출 오류를 타임아웃·요청 한도·서버 오류·기타 네 유형으로 분류해 기록하고, 사용자에게 보이는 안내는 지연과 그 외 장애 두 갈래로 단순화.
  • LLM 응답 대기 상한과 SSE 연결 유지 상한을 따로 두고 앞의 값을 더 짧게 고정해, 연결이 끊기기 전에 폴백 안내가 먼저 도달하도록 순서를 보장.
  • 호출당 토큰과 모델별 지연·에러율을 집계해 어떤 질의에서 실패가 반복되는지 확인할 수 있도록 구성.
