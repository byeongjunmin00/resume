증상이 사라진 것과 원인이 해결된 것을 구분합니다. 설정을 바꿔 문제가 보이지 않게 되면 거기서 멈추지 않고, 원인이 특정될 때까지 파고듭니다. 원인을 확인하지 않고 넘어간 문제는 언제든 다른 장애를 유발할 수 있기 때문입니다.

가설은 측정으로 검증하고, 결과가 가설과 어긋나면 폐기한 뒤 원점에서 재진단합니다. 정상 흐름만 통과한 코드는 장애가 났을 때 어떻게 되는지 모르는 상태라고 봅니다. 그래서 의존 컴포넌트를 직접 중단시키는 fault injection 으로 실패 경로까지 확인한 뒤에 동작한다고 판단합니다.

확인한 것과 아직 확인하지 못한 것을 구분합니다. 측정하지 않은 것은 측정하지 않았다고 적고, 알고 있는 한계는 결과와 함께 남깁니다. 지금까지의 검증은 토이 프로젝트 수준에 머물러 있습니다. 프로덕션 트래픽과 운영 데이터를 직접 다루고 싶습니다.

공동구매 도메인 설계 및 구현

  • 참여 인원 구간별로 단가가 내려가는 규칙을 별도 엔티티로 분리해, 상품마다 다른 할인 구간을 데이터로 정의하고 코드 변경 없이 바꿀 수 있도록 설계.
  • 여러 명이 동시에 참여할 때 정원을 넘기는 문제를 비관적 락과 원자적 UPDATE 두 방식으로 각각 구현하고, 부하테스트로 두 전략을 비교해 선택 근거를 남김.
  • 공구 성사·마감을 스케줄러로 판정하고, 정원 미달 시 자동 취소·환불로 이어지도록 구성. 결제하지 않고 자리만 차지하는 참여는 유예 시간 뒤 만료 처리.
  • 정원 변동을 커밋 이후에만 브로드캐스트해 롤백된 참여가 화면에 반영되지 않도록 이벤트 발행 시점을 고정.
결과
동시 참여가 몰려도 정원과 확정 단가가 어긋나지 않습니다.

결제 처리와 실시간 상담 구현

  • 결제 생성·조회와 환불 처리를 구현. 승인과 거절이 동시에 들어올 때 두 요청이 모두 성공하던 경합을 발견해 잠금으로 차단.
    ※ PG(PortOne) 연동 자체는 팀원 담당
  • WebSocket·STOMP 로 1:1 상담을 구현하면서, 연결·구독·발행 세 지점 모두에서 참여자 여부를 검사. 구독만 막으면 남의 방에 메시지를 밀어 넣을 수 있기 때문.
  • 메시지는 저장에 성공한 경우에만 발행되도록 순서를 고정해, 화면에는 보이는데 기록에 없는 메시지가 생기지 않도록 처리.

Redis 캐시 SPOF 제거

  • Rate Limit·인기 검색어는 Redis 장애 시 통과하도록 되어 있는데 캐시만 예외인 것을 발견. 조회 성능을 위해 붙인 캐시가 서비스 필수 의존이 되어 있던 상태.
  • Redis 를 실제로 중단시켜 상품 목록·상세가 500 을 반환하는 것을 재현.
  • 캐시 계층을 fail-open 으로 전환해 캐시 오류 시 DB 직접 조회로 넘어가도록 변경, 장애 중에도 200 응답 유지.
결과
구매자가 캐시 장애 중에도 상품 조회와 구매를 중단 없이 이어갈 수 있습니다.

프로덕션 OOM 근본 원인 규명

  • 메모리 상한을 두 차례 조정했는데도 재시작이 반복되자 설정값이 아닌 다른 원인을 의심하고, 운영 컨테이너에 직접 접속해 JVM 이 인식한 자원 값과 실제 할당량의 차이를 확인.
  • 진단 도구가 없는 런타임 이미지였던 탓에 이미지를 임시로 교체해 스레드 덤프를 확보하고, 메모리를 잠식하던 스레드가 컨테이너 자원 오인식에서 비롯된 것임을 규명.
  • JVM 이 참조하는 코어 수를 실제 할당량으로 고정. 해당 스레드가 48개 → 2개로 줄어든 것을 운영 환경에서 재측정해 확인.
결과
예측 불가능한 서버 재시작이 사라졌고, 현재 RSS 610MB / 컨테이너 한도 954MB 로 안정 가동 중입니다.

부하테스트로 한계점 규명 및 성능 가설 기각

  • k6 단계별 부하로 처리량이 정체하는 지점을 병목 신호로 잡고, 이진 탐색으로 한계 동시 사용자 수를 확정 (VU 2970 실패율 0%).
  • 병목이 DB 커넥션 풀이 아니라 애플리케이션 서버의 커넥션 수용 한계임을 특정.
  • 락 방식을 바꾸면 개선될 것이라는 가설은 측정값에 차이가 없어 기각하고, 커넥션 풀 크기와 비밀번호 해싱 비용으로 병목을 재진단.

AI 정책 문의 기능 설계 (RAG)

  • 공동구매는 인원이 모여야 성사되는 구조라 환불 조건과 성사 기준 문의가 반복될 것으로 보고, 이미 문서로 정해둔 정책을 근거로 답하는 방식을 선택. 모델이 지어내지 않도록 답변 근거를 문서로 한정.
  • similarity threshold 로는 관련 없는 질의를 거를 수 없다는 것을 전체 점수 분포를 측정해 확인. 임계값 튜닝 대신 청크 구성 방식을 바꿔 실패하던 질의를 정답 문서로 회수.
  • LLM 오류를 유형별로 분류해 이중 타임아웃과 폴백 응답을 두어 장애 시에도 안내가 도달하도록 설계. 호출당 토큰과 모델별 지연·에러율을 집계.
