Troubleshooting 01

인가를 검증하지 못하던 상담 채널 보안 테스트

상담 채널은 해당 방에 참여하지 않은 사용자에게 대화가 노출되지 않아야 합니다. 인가 로직은 구현되어 있었지만, 그것을 검증한다고 적힌 테스트가 실제로는 아무것도 검증하지 못하고 있었습니다.

01 문제

보안 테스트가 서비스 메서드를 직접 호출하고 있었습니다. 이 경로는 브로커를 경유하지 않아 브로드캐스트 자체가 발생하지 않고, 따라서 인가 로직을 제거해도 결과가 동일해 테스트가 항상 통과했습니다.

02 해결

테스트가 실제 STOMP 발행 경로를 경유하도록 전환했습니다. 이 경로에서는 브로커가 채널 구독·발행 인가를 판정하므로, 인가를 제거하면 비참여자 세션까지 메시지가 도달해 테스트가 실패합니다.

03 결과

Troubleshooting 02

힙이 아니라 스레드가 원인이었던 컨테이너 OOM

배포한 서버가 주기적으로 종료됐습니다. 최대 힙 크기(-Xmx)를 올려 해결했다고 판단했으나 47분 만에 재발했습니다.

01 문제

컨테이너가 프로세스를 종료시킨 기준은 힙이 아니라 프로세스 전체 메모리(RSS) 였습니다. JVM 이 컨테이너의 CPU 할당량을 호스트 물리 코어 수인 48로 오인식했고, 코어 수를 기준으로 산정되는 스레드풀과 GC 스레드가 그만큼 늘어났습니다. 스레드는 힙이 아니라 네이티브 영역에 스택을 잡으므로, 최대 힙 크기를 올린 조치는 힙과 네이티브의 합이 한도에 더 빨리 도달하게 만들었습니다.

02 해결

진단 도구가 없는 런타임 이미지였던 탓에 이미지를 임시로 교체해 jstack 스레드 덤프를 확보하고, 스레드를 이름별로 집계해 메시지 브로커 스레드가 과다 생성된 것을 특정했습니다. -XX:ActiveProcessorCount 를 실제 할당량으로 고정해 코어 수에 연동되는 모든 풀을 한 번에 잡고, 브로커 스레드풀 크기는 코어 수와 무관하게 별도로 지정했습니다. 해당 스레드는 48개 → 2개로 줄었습니다.

03 결과

운영 환경에서 재측정해 RSS 610MB / 컨테이너 한도 954MB 로 안정 가동하는 것을 확인했습니다. 예측 불가능한 서버 재시작이 사라졌고, 이후 OOM 은 재발하지 않았습니다.

WebSocketConfig.java · 기동 옵션
// 브로커 스레드풀 크기를 코어 수 기반 산정에 맡기지 않고 명시적으로 고정
@Override
public void configureMessageBroker(MessageBrokerRegistry registry) {
    ThreadPoolTaskScheduler scheduler = new ThreadPoolTaskScheduler();
    scheduler.setPoolSize(2);   // JVM 이 48로 오인식하던 코어 수를 대체
    scheduler.initialize();

    registry.enableSimpleBroker("/topic").setTaskScheduler(scheduler);
    registry.setApplicationDestinationPrefixes("/app");
}

Troubleshooting 03

부하테스트로 성능 한계 측정

동시 참여가 몰릴 때 어디서 먼저 무너지는지 알지 못한 상태였습니다. 처리량이 정체하는 지점을 병목 신호로 보고 한계를 실측했고, 먼저 세운 가설은 측정값이 뒤집었습니다.

01 측정

k6 로 공구팀 참여 API 에 단계별 부하를 걸었습니다. 동시 사용자를 20배 늘려도 처리량이 27.5 → 35.6 req/s 로 거의 늘지 않고 지연만 증가했습니다. 어딘가에서 요청이 순서를 기다린다는 신호로 보고, 2,500부터 이진 탐색으로 좁혀 한계점을 확정했습니다.

02 기각한 가설

정체의 원인을 락 경합이라 보고, 비관적 락을 원자적 UPDATE 로 바꾸면 처리량이 오를 것이라 가정했습니다. 같은 시나리오로 재측정한 결과는 503ms 대 486ms — 오차 범위였습니다. 개선됐다고 우기지 않고 가설을 폐기했습니다.

03 병목 특정

실패가 급증한 지점에서 p95 가 19초에서 8초로 오히려 낮아졌습니다. 커넥션을 기다리다 타임아웃난 것이라면 지연이 더 올라가야 하므로, 요청이 애플리케이션에 도달하기 전에 연결 자체가 거부된 것으로 판단했습니다. DB 커넥션 풀이 아니라 Tomcat 의 연결 수용 한계입니다.

04 남긴 한계

처리량 상한의 다음 후보로 DB 커넥션 풀 기본값(10) 과 로그인 해싱 비용을 지목했지만, 로그인을 제외한 시나리오나 풀 크기를 늘린 재측정으로 두 요인을 분리하지는 못했습니다. 서버 지표(Actuator·APM)를 붙이지 않아 설정값과 실패 패턴으로 추론한 것도 한계입니다.

Architecture

고도화 영역 분담과 상품 조회 경로

클라이언트가 REST API 또는 WebSocket 으로 요청을 전송하면 서버가 인증을 검증하고 도메인 로직을 처리합니다. 상품 조회는 제가 설계한 복합 인덱스와 FULLTEXT 인덱스를 경유합니다.

Troubleshooting 01

ORM 이 표현하지 못하는 인덱스를 기동 시점에 적용

상품명 검색을 인덱스로 처리해야 했지만, 스키마가 JPA 의 자동 생성에만 의존하고 있어 ORM 이 표현하지 못하는 DDL 을 적용할 지점이 없었습니다. 마이그레이션 도구 도입이 정석이라고 봤지만 팀 일정상 해당 주차에 반영할 수 없었고, 그 제약 안에서 안전장치를 어디까지 둘지를 판단 기준으로 삼았습니다.

01 문제

상품명 검색이 인덱스 없이 풀스캔으로 처리되고 있었습니다. JPA 의 @Index 는 BTREE 만 지원해 FULLTEXT 인덱스를 선언할 수 없었고, 스키마 변경을 버전으로 관리하는 도구가 없어 DDL 을 적용할 지점 자체가 없었습니다.

02 해결

ApplicationRunner 를 구현해 기동 시 information_schema 로 인덱스 존재 여부를 조회하고, 부재 시 ngram parser 로 FULLTEXT 인덱스를 생성하도록 했습니다. 재기동에 대해 멱등하며, MySQL 전용 조회이므로 테스트 프로파일에서는 비활성화했습니다.

03 결과

실행 계획이 풀스캔(type: ALL)에서 fulltext 로 전환된 것을 EXPLAIN 으로 확인했습니다. 데이터가 증가해도 검색 비용이 선형으로 늘지 않습니다. 다만 기동 시점 DDL 은 여러 인스턴스가 동시에 뜨면 경합이 생기고 스키마 변경 이력도 남지 않으므로 임시 방편입니다. 같은 제약을 다시 만나면 Flyway 같은 마이그레이션 도구 도입을 먼저 설득하겠습니다.

ProductFullTextIndexInitializer.java
@Component
@RequiredArgsConstructor
@Profile("!test")   // information_schema 는 MySQL 전용
public class ProductFullTextIndexInitializer
        implements ApplicationRunner {

    private static final String INDEX_NAME = "idx_product_name_fulltext";
    private final JdbcTemplate jdbcTemplate;

    @Override
    public void run(ApplicationArguments args) {
        Integer count = jdbcTemplate.queryForObject(
            "SELECT COUNT(*) FROM information_schema.statistics "
          + "WHERE table_schema = DATABASE() AND table_name = 'products' "
          + "AND index_name = ?",
            Integer.class, INDEX_NAME);

        // 이미 존재하면 생성하지 않는다 — 재기동에 대해 멱등
        if (count == null || count == 0) {
            jdbcTemplate.execute(
                "ALTER TABLE products ADD FULLTEXT INDEX " + INDEX_NAME
              + " (name) WITH PARSER ngram");
        }
    }
}

Troubleshooting 02

가격 범위·상품명 검색 API 신규 구현과 인덱스 전후 성능 검증

가격대로 상품을 조회하거나 상품명을 검색하는 사용자가 응답 지연을 겪고 있었습니다. 두 조회는 병목의 원인이 서로 달라 해법도 나뉘었습니다.

01 문제

가격 범위 조회는 인덱스가 없어 filesort 가 발생했고, 상품명 검색은 LIKE 패턴 매칭이라 풀스캔으로 처리됐습니다. 데이터가 증가할수록 두 조회 모두 비용이 선형으로 증가하는 구조였습니다.

02 해결

가격 범위 조회는 판매 상태로 걸러낸 뒤 가격으로 범위 검색하는 형태였으므로, (status, price) 복합 인덱스를 추가했습니다. 등가 조건인 status 를 선행 컬럼에, 범위 조건인 price 를 후행 컬럼에 배치해야 인덱스가 정렬까지 흡수해 range 스캔으로 동작합니다. 상품명 검색은 성질이 달라 FULLTEXT 인덱스와 네이티브 쿼리로 엔드포인트를 분리했습니다.

03 결과

가격 범위 조회의 실행 계획이 ref 와 filesort 조합에서 range 로 전환되고, 순수 SQL 실행 시간이 4.8초에서 0.09초로 단축됐습니다. 다만 페이지네이션 count 쿼리는 새 인덱스를 사용하지 않아 체감 응답시간의 개선폭이 제한적이라는 점을 한계로 함께 기록했습니다. 원인 분석까지는 진행했고, 인덱스 힌트 적용 후 재측정은 하지 못했습니다.

@Entity
